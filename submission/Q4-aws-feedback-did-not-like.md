Most of my lost hours came from errors that named a symptom but not a cause. The fixes were usually one line; finding the line took far longer. Six issues, each with a concrete suggestion.

**1. Amazon Bedrock Guardrails: say which filter fired.** My assistant never used the model at first; every question came back in the rules' plain wording. The prompt-attack filter was blocking my own rewording instruction, because I had put it in the `user` turn, which the filter reads for attacks. With the guardrail trace off (the default), the Converse response said only that the guardrail intervened, not which policy fired. Moving the instruction to the system prompt fixed it. Suggestion: name the policy type (content filter, denied topic, prompt attack, sensitive information) in every intervention, trace or not.

**2. Amazon Bedrock in ap-south-1: model ids and IAM are a two-step trap.** Calling Nova Micro by its bare model id (`amazon.nova-micro-v1:0`) is refused in Mumbai; only the inference profile `apac.amazon.nova-micro-v1:0` works. The IAM policy then needs two ARNs: the profile, and the foundation model with a wildcard region. The access-denied error names neither, and nothing on the model's console page says a profile is required in this region. Suggestion: a note on the model page, and an error that names the ARN it checked.

**3. Amazon CloudFront to Amazon API Gateway: a bare 403.** My first live call through CloudFront returned 403 with no message. CloudFront was forwarding the viewer's Host header, which API Gateway refuses. The managed origin request policy `AllViewerExceptHostHeader` exists for this, but nothing in the 403, or in the setup path I followed, points to it. Suggestion: a hint in the error, or a CDK warning when a distribution fronts an HTTP API with no explicit origin request policy.

**4. AWS CDK and CloudFormation: a deploy and its rollback both failed.** An API stage's per-route throttle settings are an untyped map, and mine named a route that the same deploy had not created yet. It passed `cdk synth` and every test. The deploy failed, and then the rollback failed too. The fix was an explicit dependency from the stage to each route. Suggestion: validate at synth time that route settings name routes that exist, and let a rollback skip a resource that cannot be rolled back instead of blocking.

**5. Amazon EventBridge Scheduler: silence on failure.** A schedule that stops firing raises nothing. I built a CloudWatch alarm on fewer than one invocation in 45 minutes, with missing data treated as breaching. Suggestion: a built-in "did not fire in N minutes" alarm per schedule, or a last-successful-invocation metric.

**6. AWS Step Functions: `states:SendTaskSuccess` cannot be scoped.** It has no resource-level permission, so my API function must hold it on `*`: a bug in that function could resume any state machine in the account. I added a CDK test that only one policy may grant it, as a compensating control. Suggestion: allow the permission to be scoped to the state machine that issued the task token.
