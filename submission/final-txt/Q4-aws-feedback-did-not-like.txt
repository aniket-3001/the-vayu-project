Six places where AWS cost me time, what each taught me, and what I would suggest. Each fix was usually one line; finding it was the work.

1. Amazon Bedrock Guardrails: knowing which filter fired. My assistant first answered only in the rules' plain wording. The prompt-attack filter was reading my own rewording instruction, which I had put in the user turn, as an attack. With the trace off (the default), the Converse response said only that the guardrail intervened. I turned the trace on, found the filter, and moved the instruction to the system prompt. What I learned: put instructions where the model expects them, and turn the trace on from day one. Suggestion: name the policy type (content filter, denied topic, prompt attack, sensitive information) in every intervention, trace or not.

2. Amazon Bedrock in ap-south-1: model ids and IAM. Nova Micro by its bare model id is refused in Mumbai; only the inference profile apac.amazon.nova-micro-v1:0 works. The IAM policy then needs two ARNs: the profile, and the foundation model with a wildcard region. The access-denied error names neither. I learned to read the cross-region inference documentation before writing the policy, not after the first error. Suggestion: a note on the model page about regions that need a profile, and an error that names the ARN it checked.

3. Amazon CloudFront to Amazon API Gateway: a 403 with no message. My first live call through CloudFront returned 403. CloudFront was forwarding the viewer's Host header, which API Gateway refuses. A custom origin request policy that forwards only the viewer address fixed it, and the managed AllViewerExceptHostHeader policy exists for the same job. The lesson was to test the live path early, because every test passed before it. Suggestion: a hint in the error, or a CDK warning when a distribution fronts an HTTP API with no explicit origin request policy.

4. AWS CDK and CloudFormation: a deploy and its rollback both failed. An API stage's per-route throttle settings are an untyped map, and mine named a route the same deploy had not created yet. cdk synth and every test passed; the deploy failed, and then the rollback failed too. The fix was an explicit dependency from the stage to each route. I learned that synth proves the template is valid, not that CloudFormation can order it, and I now deploy to see the order. Suggestion: validate at synth time that route settings name routes that exist.

5. Amazon EventBridge Scheduler: a stopped schedule is silent. Nothing is raised when a schedule stops firing, so I built a CloudWatch alarm on fewer than one invocation in 45 minutes, with missing data treated as breaching. Every polling job now gets that alarm when I build it. Suggestion: a built-in "did not fire in N minutes" alarm per schedule.

6. AWS Step Functions: states:SendTaskSuccess has no resource-level permission. My API function holds it on *. I added a CDK test that only one policy in the stack may grant it, and I now treat unscoped permissions as something a test must watch. Suggestion: allow it to be scoped to the state machine that issued the task token.
